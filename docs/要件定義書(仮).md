# 利用者情報管理・クイックアクセスアプリ 要件定義 v0.1

**作成時点：2026年10月6日**  
**ステータス：初期要件定義／担当者ヒアリング前**

## 1. 背景

対象は就労継続支援B型事業所を想定する。

現時点で把握している事業所規模は、職員10名以内、利用者15名程度である。

事業所ではGoogle Driveを利用しているが、利用者に関する重要情報のうち、どの程度がGoogle Driveに保存されているかは未確認である。

現場では、利用者に体調変化やその他の事象が発生した際、職員が必要な情報へモバイル端末から迅速にアクセスできる状態が求められている。

現在職員は全員iOS端末を利用しているが、将来的なAndroid利用も想定する。

---

# 2. アプリの目的

本アプリの主目的は、

**利用者に関する重要情報をアプリ内で管理し、職員が必要な場面で必要な情報へ短時間でアクセスできる状態を実現すること**

である。

単なる既存ファイルへのリンク集ではなく、利用者情報そのものをアプリ側で保持することを基本方針とする。

一方で、既存のGoogle Drive、紙、Excel、業務システム等との関係は、担当者ヒアリング後に確定する。

---

# 3. プロダクトの位置付け

本アプリは、

**「利用者情報管理」＋「職員向けクイックアクセス」**

の2つを中核機能とする。

概念的には以下となる。

```
利用者情報を安全に保存する
            ＋
必要な情報へ素早く到達できる
            ↓
職員向け利用者情報管理・
クイックアクセスアプリ
```

情報を保存するだけのデータベースではなく、緊急時・日常支援時の情報参照速度を重視する。

---

# 4. 想定ユーザー

## 4.1 主利用者

事業所職員。

現時点では10名以内を想定する。

## 4.2 管理者

職員アカウント、権限、利用者情報等を管理する役割を想定する。

管理者を誰が担当するか、管理者を複数人とするかは未確定。

## 4.3 利用者本人

現段階では、本アプリを利用者本人が操作することは想定していない。

職員向けアプリとして設計する。

---

# 5. 管理対象となる情報

現時点で候補となっている情報は以下。

| 情報分類   | 例              | 現状     |
| ------ | -------------- | ------ |
| 服薬情報   | 薬剤、服用方法等       | 管理対象候補 |
| 疾患情報   | 持病、既往歴等        | 管理対象候補 |
| 障害関連情報 | 障害特性、支援上必要な情報  | 管理対象候補 |
| 緊急情報   | 緊急時に優先して確認する情報 | 必要性が高い |
| 緊急連絡先  | 家族等の連絡先        | 管理対象候補 |
| 支援情報   | 日常支援上必要な情報     | 要ヒアリング |
| 個別支援計画 | 支援方針等          | 要ヒアリング |
| 添付資料   | PDF、JPG等       | 管理対象候補 |
| 組織情報   | MVV等           | 閲覧対象   |

実際にどこまで保存するかは未確定であり、担当者とのヒアリングで決定する。

---

# 6. 情報保存方針

## 6.1 基本方針

利用者情報は、原則としてアプリのバックエンド側を主要な保存先とする方向で検討する。

```
Backend / Database
      ↓
利用者情報の主要保存場所

iPhone / Android
      ↓
情報を安全に参照するクライアント
```

「アプリ内保存」は、スマートフォン端末本体へ全情報を保存することを意味しない。

## 6.2 端末への保存

利用者の医療・障害等に関する情報については、端末への永続保存を必要最小限とする方向で検討する。

オフライン閲覧は必須とする。通信できない場所や障害時にも、事前に取得した必要情報を職員が閲覧できるようにする。

端末に保持する情報の範囲、暗号化、キャッシュ期限、ログアウト時削除、端末紛失対策、更新情報の同期方法を別途定義する。

---

# 7. クイックアクセス要件

クイックアクセス性は、本アプリの必須要件とする。

理想的な基本導線は以下。

```
アプリ起動
 ↓
認証
 ↓
利用者選択
 ↓
必要情報
```

主要情報については、可能な限り少ない操作回数で到達できるUIを目指す。

利用者詳細画面では、例えば以下のような情報分類を想定する。

```
利用者A

⚠ 緊急情報

💊 服薬情報

🏥 疾患・既往歴

♿ 障害・支援情報

☎ 緊急連絡先

📄 関連資料
```

具体的な優先順位、配置、操作回数については、職員の実際の利用場面を確認した上で定義する。

---

# 8. モバイル要件

## 8.1 対応端末

現在の優先順位は以下。

```
第1優先
iPhone / iOS

第2優先
Android

必要に応じて
PC / Web
```

現在職員全員がiOSを使用しているため、iPhoneでのユーザビリティを最優先とする。

ただし将来的なAndroid利用を考慮し、iOS専用技術へ過度に依存しない構成も候補とする。

---

# 9. 認証要件

認証には一定以上のセキュリティを求める。

一方で、利用者に何か発生した際の即時アクセスが必要であるため、毎回複雑な認証操作を要求する方式は避ける。

現時点では、GoogleアカウントとPasskeyを組み合わせる認証を仮候補とする。実装方式と、オフライン時に認証済みの職員が情報を閲覧する方法は未確定。

想定するUXは、

```
アプリ起動
↓
Face ID等
↓
認証
↓
情報閲覧
```

である。

以下は未確定。

- Passkeyをアプリ独自で管理するか
- GoogleアカウントとPasskeyをどのように組み合わせるか
- セッション保持時間
- 再認証条件
- Passkey紛失時の復旧方法
- 新端末への移行方法

---

# 10. 権限管理

職員全員がすべての情報を閲覧・編集できるかは未確定。

将来的には例えば、

```
一般職員
→ 閲覧

担当職員
→ 一部情報編集

管理者
→ 全体管理
```

のようなRole Based Access Controlを検討する。

ただし、事業所規模が職員10名以内であるため、不必要に複雑な権限体系は避ける。

---

# 11. データ更新

利用者情報は時間経過によって変更されるため、更新方法を定義する必要がある。

特に、

```
服薬変更
緊急連絡先変更
疾患情報変更
支援上の注意事項変更
```

などについて、

「誰が」「いつ」「どのように」更新するかを決める必要がある。

現時点では未確定。

---

# 12. 監査・履歴

医療・障害等の重要情報を扱う可能性があるため、変更履歴を保持する方向で検討する。

例えば、

```
変更日時
変更した職員
変更前
変更後
```

などを記録する。

「誰が閲覧したか」まで監査ログを残す必要があるかは未確定。

---

# 13. Google Driveとの関係

事業所ではGoogle Driveを使用している。

ただし、

**重要な利用者情報がGoogle Driveにどの程度存在するかは現時点では不明**

である。

そのため、Google Driveをアプリの主要データ基盤として確定しない。

今後、

```
既存データ移行元

添付ファイル保存先

一部情報との連携先

バックアップ先
```

等になる可能性がある。

担当者へのヒアリング後に役割を確定する。

---

# 14. 既存情報源の確認

既存データがどこに保存されているかについては調査する。

ただし目的は既存システムをそのまま維持することではなく、

- どの情報をアプリへ移行する必要があるか
- どの情報が現在の正式情報なのか
- 誰が更新しているのか
- どのような移行作業が必要になるか

を判断するためである。

# 16. 非機能要件

## セキュリティ

医療情報・障害情報等を扱う可能性があるため、一般的な社内情報アプリより高いセキュリティを求める。

通信暗号化、認証、認可、保存データ保護、監査、バックアップ等を考慮する。

## 可用性

業務中に必要な情報へアクセスできることを重視する。

必要なサービスレベルは未確定。

## 操作性

ITに詳しくない職員でも容易に操作できることを求める。

特に緊急時に迷わない画面構成を重視する。

## パフォーマンス

利用者情報の主要画面について、待ち時間を感じにくい表示速度を目標とする。

具体的な数値目標は未確定。

## 拡張性

職員・利用者数は小規模であるため、大規模トラフィック対応を優先しない。

一方、Android対応や管理情報追加などの仕様変更には対応できる構造を目指す。

# 19. 現時点のMVP仮説

担当者ヒアリングによって変更されることを前提として、最小構成は以下を仮置きする。

## 19.1 対象となる利用場面と情報

職場で利用者に何かあったとき、職員がモバイル端末から必要な情報をすぐに閲覧できるようにする。MVPで優先する利用者情報は以下とする。

- おくすり情報：薬剤名、服用方法等の支援に必要な情報
- 疾患情報：持病、既往歴等の支援に必要な情報
- 障害に関わる情報：障害特性、支援上の注意事項等

実際の項目、表示順、情報の正式な更新元は担当者ヒアリングで決める。実在する利用者の情報を扱うため、開発中のテストデータには架空の情報を使用する。

## 19.2 職員向け画面

- 職員が利用者の一覧から対象者を選び、上記の重要情報へ少ない操作で到達できる画面を用意する。
- 重要情報を見分けやすく表示し、緊急時に迷わない導線を優先する。
- 組織のMVVへすぐにアクセスできる入口を用意する。表示方法は、JPG画像を直接表示する方式、または内容を網羅した一覧ページへ移動する方式を候補とする。

## 19.3 オフライン閲覧

- オフライン閲覧をMVPの必須機能とする。事前に取得したMVP対象情報とMVVは、通信できない状態でも閲覧できるようにする。
- 最終同期日時を表示し、オフライン中の情報が最新とは限らないことを職員が判断できるようにする。
- 端末に保持する範囲、暗号化、キャッシュ期限、ログアウト・端末紛失時の削除や利用停止、再接続時の同期方法を設計時に決める。

## 19.4 認証と情報管理

- 職員の認証はGoogleアカウントとPasskeyの組み合わせを仮候補とし、アクセスの速さを重視する。オフライン時に認証済み職員が再閲覧する方法も設計対象とする。
- 利用者情報はバックエンドを主要な保存先とし、権限のある職員が内容を更新できる最低限の管理手段を用意する。更新担当者、編集画面、権限範囲はヒアリングで決める。
- オンライン時の情報更新と端末側の同期状態を確認できるようにする。

## 19.5 MVPで確定する範囲

上記は必要な機能の仮説であり、PWA・React Native等の実装方式、詳細なデータ項目、MVVの表示方式、認証の具体的な手順は未確定とする。特にオフライン閲覧と機微情報の保護を両立できる構成を確認してから技術を選定する。
