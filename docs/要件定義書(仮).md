# 利用者情報管理・クイックアクセスアプリ 要件定義 v0.1

**作成時点：2026年10月6日**  
**ステータス：初期要件定義／担当者ヒアリング前**

## 1. 背景

対象は就労継続支援B型事業所を想定する。

現時点で把握している事業所規模は、職員10名以内、利用者15名程度である。

現在の利用者情報はすべてGoogle Driveに保存されている。アプリへの移行はIT担当者が行う。移行対象のファイルと最新版の特定方法は確認する。

果物の収穫、ワインのラベル貼り、清掃などの外作業先を含め、職員が利用者への支援のポイントをモバイル端末から確認できる状態が求められている。体調に不具合があった際にかかりつけ医や服薬情報を優先表示する機能は、将来の検討対象とする。

現在職員は全員iOSの個人所有端末を利用しているが、将来的なAndroid利用も想定する。

---

# 2. アプリの目的

本アプリの主目的は、

**職員が利用者への支援のポイントを確認できるようにすること**

である。

MVPでは、事務所が請け負う作業名をシステム内に登録し、利用者ごとに各作業の得意・苦手等を作業名と評価記号の一覧で入力・確認できるようにする。利用者ごとの「スタッフ支援ポイント」と「利用者ニーズ整理マトリクス」をJPEGとしてアップロードし、利用者情報確認ページで閲覧できるようにする。また、組織のMVV一覧ページを設け、MVVのJPEGを確認できるようにする。

作業名と、職員が経験に基づいて判断した利用者ごとの作業適性評価は、アプリ内でデータとして管理する。閲覧対象のJPEGはこれらとは別の資料としてアプリ側で管理する。

既存情報はGoogle DriveからIT担当者が初期移行する。これはDriveのファイルを確認してアプリへ登録する意味であり、Driveからの自動同期を意味しない。各利用者の移行元資料の特定方法と、資料がない場合の扱いは担当者ヒアリングで確認する。

---

# 3. プロダクトの位置付け

本アプリは、

**「利用者ごとの作業適性の入力・確認」＋「JPEG資料の閲覧」＋「組織のMVV一覧」**

の3つを中核機能とする。

概念的には以下となる。

```
作業名・利用者ごとの評価とJPEG資料を安全に管理する
            ＋
利用者情報確認ページとMVV一覧ページへ素早く到達できる
            ↓
職員が支援のポイントを確認できるアプリ
```

日常支援時に内容を読み取れることと、必要な場面ですぐに開けることを重視する。医療・緊急情報の独立した優先表示はMVPに含めない。

# 4. 想定ユーザー

## 4.1 主利用者

事業所職員。

現時点では10名以内を想定する。

## 4.2 管理者

職員アカウント、権限、利用者情報等を管理する役割を想定する。

作業名の削除とアプリ内での権限付与はIT担当者に限定する。作業評価・JPEG・ニーズの変更はIT担当者が確認して公開する。JPEG・MVVの更新操作はIT担当者またはサービス責任者が行える。現事業所でアプリを管理・運用するIT担当者は1人。初期権限の設定方法は実装時に定める。

## 4.3 利用者本人

現段階では、本アプリを利用者本人が操作することは想定していない。

職員向けアプリとして設計する。

# 5. 管理対象となる情報

MVPで扱う情報と、詳細な扱いをヒアリングで決める情報は以下。

| 情報分類   | 例              | 現状     |
| ------ | -------------- | ------ |
| 作業マスタ | 事務所が請け負う作業名 | MVP。全職員が追加・編集、IT担当者のみ削除 |
| 利用者ごとの作業評価 | 職員が経験に基づいて判断した各作業への適性を示す記号や評価 | MVP。作業名ごとの一覧で入力・閲覧 |
| 六つのニーズ・アプローチポイント | メインニーズとサブニーズの選択結果、支援のための自由記述 | MVP。アプリ内で編集 |
| スタッフ支援ポイント | 利用者の基本情報、得意・苦手な作業、支援上の注意点等を1枚にしたJPEG | MVP。モバイルから差し替え・閲覧 |
| 利用者ニーズ整理マトリクス | 利用者ごとのマトリクスのJPEG | MVP。モバイルから差し替え・閲覧 |
| 組織情報 | MVVの一覧ページとMVVのJPEG | MVP。モバイルから差し替え・閲覧 |
| 医療・緊急情報 | 服薬、かかりつけ医、疾患、緊急連絡先等 | 独立した優先表示はMVP外。既存JPEGに含まれる情報の閲覧は継続 |
| その他の支援情報 | 障害特性、個別支援計画等 | 詳細な扱いは要ヒアリング |

作業評価一覧には、作業名と次の5種類の記号を並べる。担当職員が経験に基づいて判断し、JPEG資料とは別にオンラインで入力・更新する。「⬜︎」は作業の未経験を示し、評価が入力されていない状態とは区別する。再評価を職員会議等で行うか、その時期と手順は担当者に確認する。

| 記号 | 意味 |
| --- | --- |
| ◎ | その作業に長けている |
| ◯ | 問題なくできる |
| △ | サポートが入ればできる |
| × | 苦手 |
| ⬜︎ | その作業は未経験 |

担当職員が入力した作業評価は、IT担当者の確認後に公開する。確認時には、スタッフ支援ポイントのJPEGに記された得意・苦手な作業と評価の食い違いがないかをダイアログで確認するよう促す。食い違いがあっても注意表示を付けて公開し、JPEGの記載を優先する。自動で食い違いを検出する機能は現時点で確定していない。

提示された「スタッフ支援ポイント」の様式には、氏名、年齢、診断名、利用期間、利用に至った経緯、今のステップ、得意な作業とその理由、苦手な作業、作業以外で得意なこと・苦手なこと、注意点、特徴の欄がある。実際の利用者情報をこの要件定義書に記載せず、JPEGを利用者ごとに安全に管理する。

# 6. 情報保存方針

## 6.1 基本方針

作業名と利用者ごとの作業評価はバックエンドのデータベースを主要な保存先とする。利用者ごとのJPEG資料とMVVのJPEGもアプリのバックエンド側で管理する方向で検討する。

```
Backend / Database
      ↓
作業マスタ・評価・JPEG等の主要保存場所

iPhone / Android
      ↓
情報を安全に参照するクライアント
```

「アプリ内保存」は、スマートフォン端末本体へ全情報を保存することを意味しない。

## 6.2 端末への保存

利用者の支援情報を含む評価データとJPEGについては、端末への永続保存を必要最小限とする方向で検討する。

オフライン閲覧は必須とし、全利用者分のスタッフ支援ポイントと利用者ニーズ整理マトリクス、組織のMVVの各JPEGを事前に端末へ取得し、通信できない場所でも閲覧できるようにする。情報の変更は月に数回を想定し、オンライン時に変更を確認して端末の保存版を更新する。

オフラインでのデータ編集とJPEG差し替えは行わず、オンライン時のみ可能とする。オフライン閲覧用のJPEGはサーバーから端末へ取得するものであり、オフライン中に作った未送信の編集データはない。個人所有端末を使用するため、JPEG以外の端末保存範囲、暗号化、キャッシュ期限、ログアウト時削除、端末紛失対策を別途定義する。アプリからJPEGを写真アプリ・ファイルアプリ等へ保存したり、他アプリへ共有・書き出したりする機能は設けない。OSのスクリーンショット機能まで完全に禁止できるものではないため、その扱いは別途確認する。

個人情報を「利用開始日から5年間保存して削除する」という当初案は採用しない。[松本市条例第65号の第80条第2項・第194条](https://www.city.matsumoto.nagano.jp/uploaded/attachment/122908.pdf)では、B型計画、サービス提供、市町村への通知、身体的拘束、苦情、事故に関する対象記録を、サービス提供日から5年間保存する。これは最低保存期間であり、5年経過時の一律削除を意味しない。アプリのJPEG・作業評価・ニーズ情報がどの記録に該当するか、事業所の記録運用を確認し、元データの保持・論理削除・物理削除・バックアップの扱いを決める。端末内のオフライン用キャッシュは元データの保存義務と区別する。

# 7. クイックアクセス要件

クイックアクセス性は、本アプリの必須要件とする。

理想的な基本導線は以下。

```
アプリ起動
 ↓
認証
 ↓
利用者選択
 ↓
必要情報
```

主要情報については、可能な限り少ない操作回数で到達できるUIを目指す。

プルダウンで利用者を選んだ後は、スタッフ支援ポイント、利用者ニーズ整理、作業マッチングのどの画面を開いても、その利用者の情報を表示する。別の利用者へ切り替えた場合は、これらの画面も新たに選んだ利用者の情報へ切り替える。

MVPの利用者情報確認ページでは、作業ごとの評価一覧と次の2種類のJPEGを開けるようにする。

```
利用者A

📋 作業ごとの得意・苦手等の評価一覧

📷 スタッフ支援ポイント（1枚のJPEGで閲覧）

📊 利用者ニーズ整理マトリクス
```

ホーム等からMVV一覧ページにもすぐに移動し、MVVのJPEGを閲覧できるようにする。具体的な配置、操作回数、JPEGの拡大表示方法は、職員の実際の利用場面を確認した上で定義する。

# 9. 認証要件

認証には一定以上のセキュリティを求める。

一方で、利用者に何か発生した際の即時アクセスが必要であるため、毎回複雑な認証操作を要求する方式は避ける。

現時点では、GoogleアカウントとPasskeyを組み合わせる認証を仮候補とする。オフライン閲覧では、最後の端末内認証から1時間が経過したらFace IDまたは端末パスコードで再認証を求める。1時間以内の端末ロック・アプリ再起動だけを理由とする追加の再認証は求めない。オンライン認証の実装方式は未確定。

想定するUXは、

```
アプリ起動
↓
Face ID等
↓
認証
↓
情報閲覧
```

である。

以下は未確定。

- Passkeyをアプリ独自で管理するか
- GoogleアカウントとPasskeyをどのように組み合わせるか
- オンライン時のセッション保持時間
- 端末内認証が利用できない場合の復旧方法
- Passkey紛失時の復旧方法
- 新端末への移行方法

# 10. 権限管理

作業名に関するMVPの権限は以下とする。

| 操作 | 全スタッフ | IT担当者 |
| --- | --- | --- |
| 作業名の追加・編集 | 可 | 可 |
| 作業名の削除 | 不可 | 可 |
| アプリ内での権限付与・変更 | 不可 | 可 |

IT担当者はアプリ内で職員アカウントに権限を付与・変更する。全スタッフが作業名を追加・編集できる職員権限を持ち、削除権限はIT担当者にのみ付与する。担当職員が利用者ごとの作業評価を入力し、IT担当者が確認して公開する。JPEG・MVVはIT担当者またはサービス責任者が更新できるが、公開にはIT担当者の確認を要する。サービス責任者に作業名の削除権限は付与しない。作業名を削除する際の既存の利用者評価の扱いと、削除の取り消し・履歴の扱いは設計時に決める。

現事業所は単一の事業所で、アプリのIT担当者は1人を想定する。最初のIT担当者は本人が自主的に登録する。複数テナント向けの本人確認・承認フローは設けない。初期設定では事前に決めた1つの職員アカウントだけへIT権限を付け、他の職員が自主登録によってIT権限を得られないようにする。具体的な紐付け方法は実装時に定める。

六つのニーズとアプローチポイントを編集できるのはIT担当者と、IT担当者がアプリ内で編集権限を付与した職員とする。メインニーズとサブニーズは、それぞれ「安定感」「変化・多様性」「重要感」「愛と繋がり」「成長」「貢献」の6項目から1つ選択する。同じ項目を両方で選択してよい。アプローチポイントはテキストエリアに自由入力する。

# 11. データ更新

利用者情報は時間経過によって変更されるため、更新方法を定義する必要がある。

特に、

```
作業名の追加・編集・削除
利用者ごとの作業評価の入力・変更
六つのニーズとアプローチポイントの編集
スタッフ支援ポイントと利用者ニーズ整理マトリクスのJPEG更新
MVVのJPEG更新
職員への権限付与・変更
```

などについて、

「誰が」「いつ」「どのように」更新したかを把握できるようにする必要がある。作業名の追加・編集は全スタッフ、削除と権限付与はIT担当者が行う。作業評価・JPEG（MVVを含む）・六つのニーズとアプローチポイントの変更は、IT担当者の確認後に公開する。確認待ち・公開済み・差し戻しは「通知・ステータス確認ページ」で確認でき、IT担当者は同ページで承認または拒否を行う。作業評価とJPEGに食い違いがある場合は注意表示を付けて公開し、JPEGを優先する。再評価の時期は職員会議等を候補として確認する。

更新が失敗した場合は旧版を保持する。正常に更新できた後の旧版の保存期間と確認手順は未確定。オフラインでの編集・差し替えは行わない。

# 12. 監査・履歴

医療・障害等の重要情報を扱う可能性があるため、変更履歴を保持する方向で検討する。

例えば、

```
変更日時
変更した職員
変更前
変更後
```

などを記録する。

「誰が閲覧したか」まで監査ログを残す必要があるかは未確定。

# 13. Google Driveとの関係

事業所の現在の利用者情報はすべてGoogle Driveに保存されている。

IT担当者がGoogle Drive上の資料を確認し、利用者と対応付けてアプリへ初期移行する。Driveからの自動取り込み・継続同期はMVPの確定要件ではない。移行対象のファイル、最新版、資料がない場合の扱いを担当者に確認する。Google Driveをアプリの主要データ基盤とはしない。

今後、

```
既存データ移行元（確定）

添付ファイル保存先

一部情報との連携先

バックアップ先
```

等になる可能性がある。

移行後の添付ファイル保存先、連携先、バックアップ先としての役割は、担当者へのヒアリング後に確定する。

---

# 14. 既存情報源の確認

現在の情報保存先はGoogle Driveである。IT担当者がアプリへの初期移行を行う。Drive内でのファイルの場所、最新版、利用者との対応付けを確認する。

ただし目的は既存システムをそのまま維持することではなく、

- どの情報をアプリへ移行する必要があるか
- どの情報が現在の正式情報なのか
- 誰が更新しているのか
- どのような移行作業が必要になるか

を判断するためである。

# 16. 非機能要件

## セキュリティ

医療情報・障害情報等を扱う可能性があるため、一般的な社内情報アプリより高いセキュリティを求める。

通信暗号化、認証、認可、保存データ保護、監査、バックアップ等を考慮する。

## 可用性

業務中に必要な情報へアクセスできることを重視する。

必要なサービスレベルは未確定。

## 操作性

ITに詳しくない職員でも容易に操作できることを求める。

特に緊急時に迷わない画面構成を重視する。

## パフォーマンス

利用者情報の主要画面について、待ち時間を感じにくい表示速度を目標とする。

具体的な数値目標は未確定。

## 拡張性

職員・利用者数は小規模であるため、大規模トラフィック対応を優先しない。

一方、Android対応や管理情報追加などの仕様変更には対応できる構造を目指す。

# 19. 現時点のMVP仮説

担当者ヒアリングによって変更されることを前提として、最小構成は以下を仮置きする。

## 19.1 対象となる利用場面と情報

職員が個人所有のモバイル端末で利用者への支援のポイントを確認する。MVPでは事務所が請け負う作業名をシステム内に登録し、担当職員が経験に基づいて判断した利用者ごとの作業適性を入力・閲覧できるようにする。作業名と「◎」「◯」「△」「×」「⬜︎」の評価を一覧で表示し、記号の意味も確認できるようにする。

利用者情報確認ページで閲覧するJPEG資料は以下の2種類とする。

1. 「スタッフ支援ポイント」：氏名、年齢、診断名、利用期間、利用に至った経緯、今のステップ、得意な作業とその理由、苦手な作業、作業以外で得意なこと・苦手なこと、注意点、特徴を含む1枚のJPEGをアップロード・閲覧する。作業評価一覧とは別の資料として扱い、両者の内容の整合方法はヒアリングで確認する。
2. 「利用者ニーズ整理マトリクス」：利用者ごとのマトリクスをJPEGとして閲覧する。

果物の収穫、ワインのラベル貼り、清掃などの外作業も利用場面の例となる。医療・緊急情報を独立して優先表示する機能はMVP外とする。スタッフ支援ポイントのJPEGに含まれる診断名等は資料として閲覧できる。開発中のテストデータには架空の情報を使用する。

## 19.2 職員向け画面

- 職員が利用者の一覧から対象者を選び、その利用者の情報確認ページで作業ごとの評価一覧と2種類のJPEGを開けるようにする。
- 選択した利用者をスタッフ支援ポイント、利用者ニーズ整理、作業マッチングの各画面で共通して表示し、利用者を切り替えたら各画面の表示対象も切り替える。
- 作業名を一覧で管理し、担当職員が経験に基づいて利用者ごとに◎・◯・△・×・⬜︎の評価をオンラインで入力・変更できる画面を用意する。「⬜︎」は未経験として表示し、評価未入力と区別する。担当職員による入力後、IT担当者の確認を経て公開し、確認時にはJPEGとの食い違いがないかを確かめるダイアログを表示する。JPEGと食い違う場合も注意表示を付けて公開し、内容の優先順位はJPEGを上とする。
- 六つのニーズとアプローチポイントを利用者ごとに編集できる画面をMVPに含める。IT担当者と、同担当者から編集権限を得た職員が利用する。メインニーズとサブニーズは共通の6項目からそれぞれ選択し、同じ項目を選んでもよい。アプローチポイントはテキストエリアに自由入力する。
- 作業評価・JPEG・ニーズの変更は「通知・ステータス確認ページ」に確認待ち・公開済み・差し戻しとして表示し、IT担当者が同ページで承認・拒否する。承認後に公開する。
- JPEGはスマートフォン上で文字や一覧を読めるように表示し、必要な部分を拡大できるようにする。
- IT担当者またはサービス責任者が、利用者ごとのJPEGをモバイルからアップロード・差し替えできるようにする。
- ホーム等から組織のMVV一覧ページへすぐに移動し、掲載されたMVVのJPEGを閲覧できるようにする。IT担当者またはサービス責任者がモバイルからMVVのJPEGを差し替えられるようにする。

## 19.3 オフライン閲覧

- オフライン閲覧をMVPの必須機能とする。全利用者分のスタッフ支援ポイントと利用者ニーズ整理マトリクスのJPEG、作業評価一覧、六つのニーズとアプローチポイント、およびMVVのJPEGを事前に端末へ保存する。MVV一覧ページ自体を端末へ保持するかは画面設計時に確認する。
- オンライン時にサーバー側の変更を確認し、変更された資料を端末へ取得する。各JPEGについて保存版と最終更新日時を表示し、オフライン中の情報が最新とは限らないことを職員が判断できるようにする。
- 更新用JPEGの取得が完了しない、または検証に失敗した場合は、そのファイルの旧版を残して更新失敗として表示する。現場へ出る前に全利用者分の取得状況を確認できる画面を用意し、未取得・更新失敗を知らせる。担当する作業に参加する利用者全員について、各種JPEGと作業マッチング情報が取得済みで閲覧できれば、その現場への出発を認める。担当外の利用者に未取得情報があっても、当該現場の準備完了判定には含めない。
- 長期間オンラインにならない端末でも旧版の閲覧を許可する。保存版が期限を過ぎた場合は警告を表示するが、閲覧は止めない。期限の長さは未確定とする。
- オンライン時に利用者の削除指示等のフラグを検知したら、その利用者の端末内データを削除する。職員のアクセス権が失効した場合も、オンライン時に当該職員の保存データを削除する。長期間オフラインの端末はフラグを受け取るまで旧版を閲覧できることを許容し、次回オンラインで検知した時点で削除する。フラグの具体的な定義は実装時に決める。
- オフライン用の保存版が表示できない場合は代替画像を表示し、タップすると原因が判別できる範囲でエラーと対処方法を示す。原因を特定できない場合も、ヘルプと再取得方法を示す。
- オフラインでの閲覧は、最後の端末内認証から1時間でFace IDまたは端末パスコードによる再認証を要求する。1時間以内であれば、端末ロックやアプリ再起動だけでは追加の再認証を求めない。
- 情報の変更は月に数回を想定する。オフラインでの入力・変更・JPEG差し替えは行わず、オンラインに戻ってから行う。アプリ外へのJPEGの保存・共有・書き出し機能は設けない。
- 個人所有端末に保持する範囲、暗号化、キャッシュ期限、ログアウト・端末紛失時の削除や利用停止を設計時に決める。退職処理は事務所でオンライン時に行う。端末キャッシュの保存期限は主要保存先の5年間の保存期間とは別に定める。

## 19.4 認証と情報管理

- 職員の認証はGoogleアカウントとPasskeyの組み合わせを仮候補とし、アクセスの速さを重視する。オフライン時に認証済み職員が再閲覧する方法も設計対象とする。
- 作業名の追加・編集は全スタッフに認め、削除はIT担当者に限定する。IT担当者がアプリ内で職員へ権限を付与・変更できるようにする。
- 担当職員が作業評価を入力する。JPEG・MVVはIT担当者またはサービス責任者が更新できる。六つのニーズとアプローチポイントはIT担当者および同担当者が編集権限を付与した職員が編集する。これらの変更の公開にはIT担当者の承認を要し、通知・ステータス確認ページで承認・拒否と状態確認を行う。
- 作業名と利用者ごとの評価はバックエンドで管理し、JPEGもアプリ側で管理する。現在の情報はGoogle DriveからIT担当者が移行する。
- オンライン時の情報更新と、端末が取得した資料の最終更新状態を確認できるようにする。

## 19.5 MVPで確定する範囲

作業名と利用者ごとの評価の入力・閲覧、六つのニーズとアプローチポイントの編集、スタッフ支援ポイントと利用者ニーズ整理マトリクスのJPEGのモバイル差し替え、MVV一覧ページとMVVのJPEGの閲覧・モバイル差し替えをMVPの中心とする。作業評価の5種類の記号と意味は確定した。PWA・React Native等の実装方式、各JPEGの作成手順、認証の具体的な手順は未確定とする。個人所有端末でのオフライン閲覧と利用者情報の保護を両立できる構成を確認してから技術を選定する。

## 19.6 個人所有端末の紛失・職員の退職

退職処理を事務所でオンライン時に行う前提は確定とし、削除の具体的な実施・確認方法と紛失時の運用は実装前に担当者と決める。

- 紛失時：職員が速やかにIT担当者へ連絡し、IT担当者が当該端末・職員のアプリへのオンラインアクセスを停止する。端末の紛失モードや遠隔消去は所有者が利用する端末側の手段として案内する。アプリ内キャッシュの暗号化、再認証、保持期限を設計し、通信できない紛失端末へのアクセス停止・削除は即時反映できない前提で対策する。
- 退職時：事務所で端末をオンラインにして処理する。退職する職員のアプリアカウントとセッションを停止し、アプリ内権限を回収するとともに、オフライン閲覧用に端末へ取得したJPEG等をアプリ側で削除する。未送信の編集データをサーバーへ反映する工程はない。削除の実施方法と確認方法は設計時に決める。IT担当者が退職する場合には、事業所が定める後任者へ管理権限を引き継ぐ。利用者の元データを退職に伴って削除する意味ではない。
- 個人情報の保存：主要保存先の記録ごとの法令・条例に基づく保存期間と、個人所有端末に一時保存するJPEGの期限・削除は別のルールとする。利用開始日から一律5年で削除する案は採用しない。松本市条例で対象となる記録の分類と、物理削除までの期間、バックアップの扱いを確認する。
