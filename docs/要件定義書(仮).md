# 利用者情報管理・クイックアクセスアプリ 要件定義 v0.1

**作成時点：2026年10月6日**  
**ステータス：初期要件定義／担当者ヒアリング前**

## 1. 背景

対象は就労継続支援B型事業所を想定する。

現時点で把握している事業所規模は、職員10名以内、利用者15名程度である。

現在の利用者情報はすべてGoogle Driveに保存されている。普段はドキュメント形式のファイルにJPG画像を埋め込んで管理し、作業マッチングだけはドキュメント内で作成している。アプリへの初期移行はIT担当者に任せ、移行元の資料と最新版は同担当者が判断する。移行のために職員間で細かな判定規則や別の承認者を定めることは必須としない。

果物の収穫、ワインのラベル貼り、清掃などの外作業先を含め、職員が利用者への支援のポイントをモバイル端末から確認できる状態が求められている。体調に不具合があった際にかかりつけ医や服薬情報を優先表示する機能は、将来の検討対象とする。

現在職員は全員iOSの個人所有端末を利用しているが、将来的なAndroid利用も想定する。

---

# 2. アプリの目的

本アプリの主目的は、

**職員が利用者への支援のポイントを確認できるようにすること**

である。

MVPでは、事務所が請け負う作業名をシステム内に登録し、利用者ごとに各作業の得意・苦手等を作業名と評価記号の一覧で入力・確認できるようにする。利用者ごとの「スタッフ支援ポイント」と「利用者ニーズ整理マトリクス」をPDFを基本形式として登録し、利用者情報確認ページで閲覧できるようにする。また、組織のMVV一覧ページを設け、MVVのPDFを確認できるようにする。

作業名と、職員が経験に基づいて判断した利用者ごとの作業適性評価は、アプリ内でデータとして管理する。閲覧対象のPDFはこれらとは別の資料としてアプリ側で管理する。

既存情報はGoogle DriveからIT担当者が初期移行する。ドキュメントに埋め込まれたJPG等はIT担当者がPDF資料として用意して登録し、ドキュメント内で作成された作業マッチングは作業名と利用者ごとの評価として入力する。移行元の資料と最新版はIT担当者が判断する。初期移行後はアプリで公開された情報を現行版とし、Drive上の資料は移行元として残す。アプリでの更新をDriveへ自動反映せず、Driveの変更もアプリへ自動同期しない。資料が未登録でもアプリの利用を続けられるようにする。

---

# 3. プロダクトの位置付け

本アプリは、

**「利用者ごとの作業適性の入力・確認」＋「PDF資料の閲覧」＋「組織のMVV一覧」**

の3つを中核機能とする。

概念的には以下となる。

```
作業名・利用者ごとの評価とPDF資料を安全に管理する
            ＋
利用者情報確認ページとMVV一覧ページへ素早く到達できる
            ↓
職員が支援のポイントを確認できるアプリ
```

日常支援時に内容を読み取れることと、必要な場面ですぐに開けることを重視する。医療・緊急情報の独立した優先表示はMVPに含めない。

# 4. 想定ユーザー

## 4.1 主利用者

事業所職員。

現時点では10名以内を想定する。

全職員が全利用者の情報を閲覧できる。

## 4.2 管理者

職員アカウント、権限、利用者情報等を管理する役割を想定する。

作業名の削除と通常のアプリ内権限付与はIT担当者に限定する。IT担当者の不在・退職に伴う引き継ぎでは、サービス管理者ロールを持つ職員がアプリ内の引き継ぎボタンから新たなIT担当者を指定する。作業評価・PDF・ニーズの変更はIT担当者が確認して公開する。PDF・MVVの更新操作はIT担当者またはサービス責任者が行える。現事業所でアプリを管理・運用するIT担当者は1人。初期権限の設定方法は実装時に定める。

## 4.3 利用者本人

現段階では、本アプリを利用者本人が操作することは想定していない。

職員向けアプリとして設計する。

# 5. 管理対象となる情報

MVPで扱う情報と、詳細な扱いをヒアリングで決める情報は以下。

| 情報分類   | 例              | 現状     |
| ------ | -------------- | ------ |
| 作業マスタ | 事務所が請け負う作業名 | MVP。全職員が追加・編集、IT担当者のみ削除 |
| 利用者ごとの作業評価 | 職員が経験に基づいて判断した各作業への適性を示す記号や評価 | MVP。作業名ごとの一覧で入力・閲覧 |
| 六つのニーズ・アプローチポイント | メインニーズとサブニーズの選択結果、支援のための自由記述 | MVP。アプリ内で編集 |
| 六つのニーズの共通参考資料 | 「シックスヒューマンニーズによる 利用者支援の可能性」（横長・11ページのPDF） | MVP。アプリ内で閲覧し、開いたときは3ページ目を表示 |
| スタッフ支援ポイント | 利用者の基本情報、得意・苦手な作業、支援上の注意点等をまとめた資料 | MVP。PDFを基本形式としてモバイルから差し替え・閲覧 |
| 利用者ニーズ整理マトリクス | 利用者ごとのマトリクス資料 | MVP。PDFを基本形式としてモバイルから差し替え・閲覧 |
| 組織情報 | MVVの一覧ページとMVVのPDF | MVP。PDFを基本形式としてモバイルから差し替え・閲覧 |
| 医療・緊急情報 | 服薬、かかりつけ医、疾患、緊急連絡先等 | 独立した優先表示はMVP外。既存PDFに含まれる情報の閲覧は継続 |
| その他の支援情報 | 障害特性、個別支援計画等 | 詳細な扱いは要ヒアリング |

作業評価一覧には、作業名と次の5種類の記号を並べる。担当職員が経験に基づいて判断し、PDF資料とは別にオンラインで入力・更新する。「⬜︎」は作業の未経験を示し、評価が入力されていない状態とは区別する。再評価を職員会議等で行うか、その時期と手順は担当者に確認する。

| 記号 | 意味 |
| --- | --- |
| ◎ | その作業に長けている |
| ◯ | 問題なくできる |
| △ | サポートが入ればできる |
| × | 苦手 |
| ⬜︎ | その作業は未経験 |

担当職員が入力した作業評価は、IT担当者の確認後に公開する。確認時には、スタッフ支援ポイントのPDFに記された得意・苦手な作業と評価の食い違いがないかをダイアログで確認するよう促す。食い違いがあっても注意表示を付けて公開し、PDFの記載を優先する。自動で食い違いを検出する機能は現時点で確定していない。

提示された「スタッフ支援ポイント」の様式には、氏名、年齢、診断名、利用期間、利用に至った経緯、今のステップ、得意な作業とその理由、苦手な作業、作業以外で得意なこと・苦手なこと、注意点、特徴の欄がある。実際の利用者情報をこの要件定義書に記載せず、PDFを利用者ごとに安全に管理する。

# 6. 情報保存方針

## 6.1 基本方針

Google Drive上の資料を移行元として残し、初期移行後の現行版はアプリで管理する。作業名と利用者ごとの作業評価はバックエンドのデータベースで管理し、利用者ごとのPDF資料とMVVのPDFもアプリのバックエンド側で管理する。Driveの移行元とアプリの現行版が異なる場合、職員が業務で参照するのはアプリの公開済み現行版とする。

```
Backend / Database
      ↓
作業マスタ・評価とPDF等のアプリ側コピーの保存場所

iPhone / Android
      ↓
情報を安全に参照するクライアント
```

「アプリ内保存」は、スマートフォン端末本体へ全情報を保存することを意味しない。

## 6.2 端末への保存

利用者の支援情報を含む評価データとPDFについては、オフライン閲覧に必要な範囲を端末へ保存する。端末の保存版はDrive上の移行元資料やアプリのバックエンド上の現行版と区別する。

オフライン閲覧は必須とし、全利用者分のスタッフ支援ポイントと利用者ニーズ整理マトリクス、組織のMVVの各PDFを事前に端末へ取得し、通信できない場所でも閲覧できるようにする。情報の変更は月に数回を想定し、オンライン時に変更を確認して端末の保存版を更新する。

オフラインでのデータ編集とPDF差し替えは行わず、オンライン時のみ可能とする。オフライン閲覧用のPDFはサーバーから端末へ取得するものであり、オフライン中に作った未送信の編集データはない。個人所有端末を使用するため、PDF以外の端末保存範囲、暗号化、キャッシュ期限、ログアウト時削除、端末紛失対策を別途定義する。アプリからPDFを写真アプリ・ファイルアプリ等へ保存したり、他アプリへ共有・書き出したりする機能は設けない。OSのスクリーンショット機能まで完全に禁止できるものではないため、その扱いは別途確認する。

個人情報を「利用開始日から5年間保存して削除する」という当初案は採用しない。[松本市条例第65号の第80条第2項・第194条](https://www.city.matsumoto.nagano.jp/uploaded/attachment/122908.pdf)では、B型に準用される対象記録について、サービス提供日から5年間の保存が求められる。事業所では、利用者ごとのPDF資料・作業評価・ニーズ情報を正式な支援記録として扱う。ただし、これらの資料すべてが条例に列挙された記録へ直接該当するとの法的判断はしていない。以下の保存期間は、対象記録の法定期間を下回らないよう設ける**本アプリの運用ルール**である。

## 6.3 アプリの現行版・履歴の保存と削除

- 対象は、利用者ごとのPDF資料、作業評価、六つのニーズとアプローチポイント、およびそれらの過去版・変更履歴とする。組織共通のMVV・参考PDFは利用者記録とは分けて管理する。
- 利用中の利用者の記録は削除しない。利用終了時にアプリ側の記録をアーカイブし、通常の利用者一覧と端末への同期対象から外す。過去の正式記録は上書きで失わず、必要な版を残す。
- 利用終了日と最終サービス提供日は、サービス管理者ロールを持つ職員またはIT担当者がオンラインで登録・訂正する。利用終了日の登録を端末への削除指示とアーカイブの起点とし、最終サービス提供日を保存期限の計算に使う。訂正前後の値・操作した職員・日時を履歴に残す。
- アーカイブした記録は、**最終サービス提供日から5年を経過するまで**アプリのバックエンドで保持する。最終サービス提供日が未登録の場合や、より長い保存義務・調査・紛争対応による保全が必要な場合は削除しない。この5年はアプリの運用上の最低期間であり、全資料に法律上一律の5年保存義務があるという意味ではない。
- 5年経過後はIT担当者が削除候補を確認し、保全の必要がなければ別の職員であるサービス管理者ロールの承認を得て論理削除する。同じ職員による削除申請と承認は許可しない。論理削除後30日以内にアプリの通常保存領域から物理削除し、バックアップからもその後30日以内に消去する。バックアップから復旧した場合も削除済みの記録を再公開しない。削除・承認の日時と担当者を、個人情報を最小限にした操作履歴に残す。保存を延長した場合は理由と次回確認日を記録する。
- Drive上の移行元資料は残し、その破棄は本アプリの対象外とする。アプリ側の記録とDriveの移行元資料のどちらか一方の削除を、他方へ自動反映しない。
- 利用終了、誤登録、アクセス権の失効などによる削除指示をオンラインで受信した端末は、対象のオフライン用キャッシュを自動削除する。通信できない間は指示を受け取れないため、次回オンライン時に実行する。端末キャッシュの削除と、バックエンドの正式記録の保存は別の処理とする。

# 7. クイックアクセス要件

クイックアクセス性は、本アプリの必須要件とする。

理想的な基本導線は以下。

```
アプリ起動
 ↓
認証
 ↓
利用者選択
 ↓
必要情報
```

主要情報については、可能な限り少ない操作回数で到達できるUIを目指す。

プルダウンで利用者を選んだ後は、スタッフ支援ポイント、利用者ニーズ整理、作業マッチングのどの画面を開いても、その利用者の情報を表示する。別の利用者へ切り替えた場合は、これらの画面も新たに選んだ利用者の情報へ切り替える。

MVPの利用者情報確認ページでは、作業ごとの評価一覧と次の2種類のPDFを開けるようにする。

```
利用者A

📋 作業ごとの得意・苦手等の評価一覧

📄 スタッフ支援ポイント（PDFで閲覧）

📄 利用者ニーズ整理マトリクス
```

ホーム等からMVV一覧ページにもすぐに移動し、MVVのPDFを閲覧できるようにする。具体的な配置、操作回数、PDFの拡大表示方法は、職員の実際の利用場面を確認した上で定義する。

六つのニーズ画面からは、職員共通の参考資料「シックスヒューマンニーズによる 利用者支援の可能性」を開けるようにする。提供された原本は11ページの横長PDFで、6項目の説明、支援例、アセスメント手順等を含む。開いたときは3ページ目をデフォルトで表示し、他のページにも移動できるようにする。利用者ごとのニーズ選択結果やアプローチポイントとは別の資料として扱う。

# 9. 認証要件

認証には一定以上のセキュリティを求める。

一方で、利用者に何か発生した際の即時アクセスが必要であるため、毎回複雑な認証操作を要求する方式は避ける。

現時点では、GoogleアカウントとPasskeyを組み合わせる認証を仮候補とする。オフライン閲覧では、最後の端末内認証から1時間が経過したらFace IDまたは端末パスコードで再認証を求める。1時間以内の端末ロック・アプリ再起動だけを理由とする追加の再認証は求めない。オンライン認証の実装方式は未確定。

想定するUXは、

```
アプリ起動
↓
Face ID等
↓
認証
↓
情報閲覧
```

である。

以下は未確定。

- Passkeyをアプリ独自で管理するか
- GoogleアカウントとPasskeyをどのように組み合わせるか
- オンライン時のセッション保持時間
- 端末内認証が利用できない場合の復旧方法
- Passkey紛失時の復旧方法
- 新端末への移行方法

## 9.1 認証方式の公式資料確認（2026年10月8日）

- [GoogleのOpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)は、Googleアカウントを使った本人確認とIDトークンの検証に利用できる。職員の許可はアプリ側の在籍アカウント・権限と照合する。GoogleへのサインインにPasskeyを使ったかどうかは常に保証されるわけではなく、認証方法を示す `amr` は追加の要求と設定が必要な任意の情報である。
- アプリがPasskey利用を必須にするなら、[WebAuthn/Passkeyの登録とサーバー側での認証結果の検証](https://developers.google.com/identity/passkeys/developer-guides/server-authentication)を、Googleでの本人確認とは別に設計する必要がある。Passkeyのオンライン認証にはサーバーが発行するチャレンジを使うため、オフラインでの1時間ごとの再認証とは分ける。
- iOSでは[Local Authentication](https://developer.apple.com/documentation/localauthentication)によりFace IDまたは端末パスコードで端末内の本人確認ができる。PWAで同等のオフライン体験と保存データの保護を実現できるかは、PWA/React Native選定時に試作して確認する。
- 推奨する検討順は「Googleで職員アカウントを識別する」「アプリ独自のPasskeyを必須にするか決める」「端末内のオフライン認証と新端末復旧を検証する」とする。現段階ではGoogleとPasskeyの具体的な組み合わせを確定しない。

# 10. 権限管理

作業名に関するMVPの権限は以下とする。

| 操作 | 全スタッフ | IT担当者 | サービス管理者ロール | 事前指定の引き継ぎ代理 |
| --- | --- | --- | --- | --- |
| 作業名の追加・編集 | 可 | 可 | 可 | 可 |
| 作業名の削除 | 不可 | 可 | 不可 | 不可 |
| 通常のアプリ内権限付与・変更 | 不可 | 可 | 不可 | 不可 |
| IT担当者の引き継ぎ先の指定 | 不可 | 不可 | 可 | サービス管理者が利用不能な場合のみ可 |
| 利用終了日・最終サービス提供日の登録・訂正 | 不可 | 可 | 可 | 不可 |

IT担当者はアプリ内で職員アカウントに権限を付与・変更する。全スタッフが作業名を追加・編集できる職員権限を持ち、削除権限はIT担当者にのみ付与する。担当職員が利用者ごとの作業評価を入力し、IT担当者が確認して公開する。PDF・MVVはIT担当者またはサービス責任者が更新できるが、公開にはIT担当者の確認を要する。サービス責任者に作業名の削除権限は付与しない。作業名を削除しても、既存の利用者評価は履歴として残す。履歴の表示方法と削除の取り消し手順は詳細定義で決める。

IT担当者自身が作業評価・PDF・ニーズを変更した場合は、本人の確認で公開できる。別の職員による承認は求めない。

現事業所は単一の事業所で、アプリのIT担当者は1人を想定する。最初のIT担当者は本人が自主的に登録する。複数テナント向けの本人確認・承認フローは設けない。初期設定では事前に決めた1つの職員アカウントだけへIT権限を付け、他の職員が自主登録によってIT権限を得られないようにする。具体的な紐付け方法は実装時に定める。

### 10.1 IT担当者の引き継ぎ

- アプリ内の「サービス管理者ロール」は、IT担当者の後任指定と、保存期間を終えた正式記録の削除承認に用いる。PDFの更新ができる「サービス責任者」とは別の権限として管理し、同じ職員が両方のロールを持つこともできる。初期設定でIT担当者以外の職員1人以上をサービス管理者に指定し、最後のサービス管理者の権限を外す前には後任を指定する。サービス管理者は在籍中の職員を1人以上「引き継ぎ代理」に事前指定する。
- IT担当者の不在・退職時は、サービス管理者がオンラインでアプリ内の「IT担当者を引き継ぐ」ボタンを開き、在籍中の職員アカウントから後任を選ぶ。確定前5分以内に採用済みのオンライン本人認証手段で再認証し、後任の氏名・アカウント、失効する旧IT担当者、権限変更内容を確認して確定する。端末内の1時間の閲覧用認証だけでは、この操作を許可しない。
- 確定時には、新担当者へのIT権限付与と旧担当者からのIT権限回収を一つの処理として行う。失敗時は両方を元に戻し、IT担当者が不在となる中途状態を作らない。旧担当者のオンラインセッションを失効させ、承認待ちの案件は新担当者の通知・ステータス確認ページへ引き継ぐ。旧担当者が職員として在籍し、閲覧権限を持ち続ける場合は閲覧用キャッシュを保持できる。退職等でアプリの利用権限も失う場合は、次回オンラインでその端末のキャッシュを自動削除する。
- サービス管理者が全員利用できない場合は、事前指定された引き継ぎ代理が同じオンライン再認証・確認手順で後任のIT担当者を指定できる。代理操作では利用不能の理由の入力を必須とし、代理には通常の権限付与や記録削除の承認権限を与えない。新IT担当者は就任後にサービス管理者の再指定を行う。
- 操作履歴には、実行者、代理操作の理由、旧・新IT担当者、日時、再認証結果、成功・失敗を残す。引き継ぎ後は新IT担当者とサービス管理者へアプリ内で結果を通知する。

六つのニーズとアプローチポイントを編集できるのはIT担当者と、IT担当者がアプリ内で編集権限を付与した職員とする。メインニーズとサブニーズは、それぞれ「安定感」「変化・多様性」「重要感」「愛と繋がり」「成長」「貢献」の6項目から1つ選択する。同じ項目を両方で選択してよい。アプローチポイントはテキストエリアに自由入力する。

# 11. データ更新

利用者情報は時間経過によって変更されるため、更新方法を定義する必要がある。

特に、

```
作業名の追加・編集・削除
利用者ごとの作業評価の入力・変更
六つのニーズとアプローチポイントの編集
スタッフ支援ポイントと利用者ニーズ整理マトリクスのPDF更新
MVVのPDF更新
六つのニーズの共通参考PDFの更新
職員への権限付与・変更
```

などについて、

「誰が」「いつ」「どのように」更新したかを把握できるようにする必要がある。作業名の追加・編集は全スタッフ、削除と権限付与はIT担当者が行う。作業評価・PDF（MVVを含む）・六つのニーズとアプローチポイントの変更は、IT担当者の確認後に公開する。確認待ち・公開済み・差し戻しは「通知・ステータス確認ページ」で確認でき、IT担当者は同ページで承認または拒否を行う。作業評価とPDFに食い違いがある場合は注意表示を付けて公開し、PDFを優先する。再評価の時期は職員会議等を候補として確認する。

IT担当者が自身で変更した内容は本人が同ページで確認し、公開できる。確認者と確認日時を記録する。

更新が失敗した場合は旧版を保持する。正常に更新できた後の旧版の保存期間と確認手順は未確定。オフラインでの編集・差し替えは行わない。

# 12. 監査・履歴

利用者の正式な支援記録を扱うため、変更履歴を保持する。IT担当者の引き継ぎ操作と、保存期間終了後の削除申請・承認・実行も記録する。

例えば、

```
変更日時
変更した職員
変更前
変更後
```

などを記録する。

利用者の記録・PDFについては、誰が、いつ、どの利用者のどの情報を開いたかを閲覧履歴として残す。オフライン閲覧時の履歴は端末内に保護して記録し、次回オンライン時にバックエンドへ送信する。通信できないまま端末を紛失・消去した場合は未送信分を回収できないため、その旨を監査上の制約として扱う。閲覧履歴の保存期間と閲覧権限は詳細定義で決める。

# 13. Google Driveとの関係

事業所の現在の利用者情報はすべてGoogle Driveに保存されている。

現在はドキュメント形式のファイルにJPG画像を埋め込んで管理している。作業マッチングは画像ではなく、ドキュメント内で作成している。ドキュメントの具体的なファイル形式、PDFとして登録する際の画質、MVVの原本形式は初期移行前に現物で確認する。

IT担当者がGoogle Drive上の資料を確認し、利用者と対応付けてアプリへ手動で初期移行する。移行元の資料と最新版の判断はIT担当者に任せる。JPG等の元資料はIT担当者がPDFとして用意し、「利用者を選ぶ → PDFを選んでアップロードする → 利用者名とPDFを確認して登録する」手順で保存する。作業マッチングはドキュメント内の内容を見ながら作業名と利用者ごとの評価をアプリに入力する。登録者と登録日時を記録する。ドキュメントからの画像抽出や作業マッチングの自動解析・変換、資料の不足や新旧の自動判定、別の職員による移行承認はMVPの必須要件としない。初期移行はIT担当者の登録操作で完了し、登録後の通常の変更には第11章の公開前確認を適用する。初期移行後はアプリで公開された情報を現行版として扱う。Drive上の移行元資料は残すが、両者の自動同期はMVPに含めない。

今後、

```
既存データ移行元（確定）

添付ファイル保存先

一部情報との連携先

バックアップ先
```

等になる可能性がある。

Google Drive上の移行元資料は維持し、移行後の現行版はアプリのバックエンドで管理する。Driveをアプリのバックアップ先や連携先として使うかは、詳細定義で決める。Driveの移行元資料の破棄手順は本アプリの範囲外とする。

# 14. 既存情報源の確認

現在の情報保存先はGoogle Drive上のドキュメントである。JPGはドキュメントに埋め込まれ、作業マッチングだけはドキュメント内で作成されている。IT担当者がPDF資料の用意と作業マッチングの入力を含む手動の初期移行を行い、Drive内の資料と利用者の対応付けおよび最新版の判断を担当する。事前の細かな判定規則や別の移行承認者を設けない。

ただし目的は既存システムをそのまま維持することではなく、

- どの情報をアプリへ移行する必要があるか
- どの情報が現在の正式情報なのか
- 誰が更新しているのか
- どのような移行作業が必要になるか

を判断するためである。

# 16. 非機能要件

## セキュリティ

医療情報・障害情報等を扱う可能性があるため、一般的な社内情報アプリより高いセキュリティを求める。

通信暗号化、認証、認可、保存データ保護、監査、バックアップ等を考慮する。

## 可用性

業務中に必要な情報へアクセスできることを重視する。

バックアップからの復旧目標は、復旧が必要な障害を検知してから**1か月以内**とする。これは復旧所要時間の上限であり、バックアップを何時間・何日前の状態まで戻せるかという目標は別途決める。通常の障害中も現場で閲覧できるよう、取得済みのオフライン情報を保持する。その他のサービスレベルは詳細定義で決める。

## 操作性

ITに詳しくない職員でも容易に操作できることを求める。

特に緊急時に迷わない画面構成を重視する。

## パフォーマンス

利用者情報の主要画面について、待ち時間を感じにくい表示速度を目標とする。

具体的な数値目標は未確定。

## 拡張性

職員・利用者数は小規模であるため、大規模トラフィック対応を優先しない。

一方、Android対応や管理情報追加などの仕様変更には対応できる構造を目指す。

# 19. 現時点のMVP仮説

担当者ヒアリングによって変更されることを前提として、最小構成は以下を仮置きする。

## 19.1 対象となる利用場面と情報

職員が個人所有のモバイル端末で利用者への支援のポイントを確認する。MVPでは事務所が請け負う作業名をシステム内に登録し、担当職員が経験に基づいて判断した利用者ごとの作業適性を入力・閲覧できるようにする。作業名と「◎」「◯」「△」「×」「⬜︎」の評価を一覧で表示し、記号の意味も確認できるようにする。

利用者情報確認ページで閲覧するPDF資料は以下の2種類とする。

1. 「スタッフ支援ポイント」：氏名、年齢、診断名、利用期間、利用に至った経緯、今のステップ、得意な作業とその理由、苦手な作業、作業以外で得意なこと・苦手なこと、注意点、特徴を含むPDFをアップロード・閲覧する。作業評価一覧とは別の資料として扱い、両者の内容の整合方法はヒアリングで確認する。
2. 「利用者ニーズ整理マトリクス」：利用者ごとのマトリクスをPDFとして閲覧する。

果物の収穫、ワインのラベル貼り、清掃などの外作業も利用場面の例となる。医療・緊急情報を独立して優先表示する機能はMVP外とする。スタッフ支援ポイントのPDFに含まれる診断名等は資料として閲覧できる。開発中のテストデータには架空の情報を使用する。

## 19.2 職員向け画面

- 職員が利用者の一覧から対象者を選び、その利用者の情報確認ページで作業ごとの評価一覧と2種類のPDFを開けるようにする。
- 利用者のPDFや作業評価がまだ登録されていない場合は、その項目に「未登録」と表示し、他の情報の閲覧とアプリの利用を続けられるようにする。「⬜︎」（その作業は未経験）と評価未登録は区別する。
- 選択した利用者をスタッフ支援ポイント、利用者ニーズ整理、作業マッチングの各画面で共通して表示し、利用者を切り替えたら各画面の表示対象も切り替える。
- 作業名を一覧で管理し、担当職員が経験に基づいて利用者ごとに◎・◯・△・×・⬜︎の評価をオンラインで入力・変更できる画面を用意する。「⬜︎」は未経験として表示し、評価未入力と区別する。担当職員による入力後、IT担当者の確認を経て公開し、確認時にはPDFとの食い違いがないかを確かめるダイアログを表示する。PDFと食い違う場合も注意表示を付けて公開し、内容の優先順位はPDFを上とする。
- 六つのニーズとアプローチポイントを利用者ごとに編集できる画面をMVPに含める。IT担当者と、同担当者から編集権限を得た職員が利用する。メインニーズとサブニーズは共通の6項目からそれぞれ選択し、同じ項目を選んでもよい。アプローチポイントはテキストエリアに自由入力する。
- 六つのニーズ画面から、職員共通の11ページPDF「シックスヒューマンニーズによる 利用者支援の可能性」をアプリ内で開けるようにする。最初に3ページ目を表示し、ページ送りと拡大表示に対応し、利用者ごとのニーズ情報と混同しない表示にする。
- 作業評価・PDF・ニーズの変更は「通知・ステータス確認ページ」に確認待ち・公開済み・差し戻しとして表示し、IT担当者が同ページで承認・拒否する。IT担当者自身の変更も本人の確認で公開できる。
- PDFはスマートフォン上で文字や一覧を読めるように表示し、必要な部分を拡大できるようにする。
- IT担当者またはサービス責任者が、利用者ごとのPDFをモバイルからアップロード・差し替えできるようにする。
- ホーム等から組織のMVV一覧ページへすぐに移動し、掲載されたMVVのPDFを閲覧できるようにする。IT担当者またはサービス責任者がモバイルからMVVのPDFを差し替えられるようにする。

## 19.3 オフライン閲覧

- オフライン閲覧をMVPの必須機能とする。全利用者分のスタッフ支援ポイントと利用者ニーズ整理マトリクスのPDF、作業評価一覧、六つのニーズとアプローチポイント、職員共通の「シックスヒューマンニーズによる 利用者支援の可能性」のPDF、およびMVVのPDFを事前に端末へ保存する。MVV一覧ページ自体を端末へ保持するかは画面設計時に確認する。
- オンライン時にサーバー側の変更を確認し、変更された資料を端末へ取得する。各PDFについて保存版と最終更新日時を表示し、オフライン中の情報が最新とは限らないことを職員が判断できるようにする。
- 更新用PDFの取得が完了しない、または検証に失敗した場合は、そのファイルの旧版を残して更新失敗として表示する。現場へ出る前に全利用者分の取得状況を確認できる画面を用意し、未取得・更新失敗を知らせる。担当する作業に参加する利用者全員について、各種PDFと作業マッチング情報が取得済みで閲覧できれば、その現場への出発を認める。担当外の利用者に未取得情報があっても、当該現場の準備完了判定には含めない。担当する利用者の必須情報が「未登録」の場合は準備完了とは表示しないが、アプリの他の情報は利用できる。
- 長期間オンラインにならない端末でも旧版の閲覧を許可する。保存版が期限を過ぎた場合は警告を表示するが、閲覧は止めない。期限の長さは未確定とする。
- オンライン時に利用者の削除指示等のフラグを検知したら、その利用者の端末内データを削除する。職員のアクセス権が失効した場合も、オンライン時に当該職員の保存データを削除する。長期間オフラインの端末はフラグを受け取るまで旧版を閲覧できることを許容し、次回オンラインで検知した時点で削除する。フラグの具体的な定義は実装時に決める。
- オフライン用の保存版が表示できない場合は代替画像を表示し、タップすると原因が判別できる範囲でエラーと対処方法を示す。原因を特定できない場合も、ヘルプと再取得方法を示す。
- オフラインでの閲覧は、最後の端末内認証から1時間でFace IDまたは端末パスコードによる再認証を要求する。1時間以内であれば、端末ロックやアプリ再起動だけでは追加の再認証を求めない。
- 情報の変更は月に数回を想定する。オフラインでの入力・変更・PDF差し替えは行わず、オンラインに戻ってから行う。アプリ外へのPDFの保存・共有・書き出し機能は設けない。
- 個人所有端末に保持する範囲、暗号化、キャッシュ期限、ログアウト・端末紛失時の削除や利用停止を設計時に決める。退職処理は事務所でオンライン時に行う。端末キャッシュの保存期限は正式な支援記録の保存期間とは別に定める。

## 19.4 認証と情報管理

- 職員の認証はGoogleアカウントとPasskeyの組み合わせを仮候補とし、アクセスの速さを重視する。オフライン時に認証済み職員が再閲覧する方法も設計対象とする。
- 作業名の追加・編集は全スタッフに認め、削除はIT担当者に限定する。IT担当者がアプリ内で職員へ通常の権限を付与・変更できるようにする。IT担当者の引き継ぎだけはサービス管理者ロールの職員が実行する。
- 担当職員が作業評価を入力する。利用者ごとのPDF・MVV・職員共通の六つのニーズ参考PDFはIT担当者またはサービス責任者が更新できる。六つのニーズとアプローチポイントはIT担当者および同担当者が編集権限を付与した職員が編集する。これらの変更の公開にはIT担当者の承認を要し、通知・ステータス確認ページで承認・拒否と状態確認を行う。
- 作業名と利用者ごとの評価はバックエンドで管理し、PDFもアプリ側で管理する。現在の情報はGoogle DriveからIT担当者が移行する。初期移行後はアプリの公開済み情報を業務上の現行版とし、Driveは移行元資料の保管場所とする。
- オンライン時の情報更新と、端末が取得した資料の最終更新状態を確認できるようにする。

## 19.5 MVPで確定する範囲

作業名と利用者ごとの評価の入力・閲覧、六つのニーズとアプローチポイントの編集、職員共通の六つのニーズ参考PDFの閲覧、スタッフ支援ポイントと利用者ニーズ整理マトリクスのPDFのモバイル差し替え、MVV一覧ページとMVVのPDFの閲覧・モバイル差し替えをMVPの中心とする。作業評価の5種類の記号と意味は確定した。PWA・React Native等の実装方式、各PDFの作成手順、認証の具体的な手順は未確定とする。個人所有端末でのオフライン閲覧と利用者情報の保護を両立できる構成を確認してから技術を選定する。

## 19.6 個人所有端末の紛失・職員の退職

退職処理を事務所でオンライン時に行う前提は確定とし、削除の具体的な実施・確認方法と紛失時の運用は実装前に担当者と決める。

- 紛失時：職員が速やかにIT担当者へ連絡し、IT担当者が当該端末・職員のアプリへのオンラインアクセスを停止する。端末の紛失モードや遠隔消去は所有者が利用する端末側の手段として案内する。アプリ内キャッシュの暗号化、再認証、保持期限を設計し、通信できない紛失端末へのアクセス停止・削除は即時反映できない前提で対策する。
- 退職時：事務所で端末をオンラインにして処理する。退職する職員のアプリアカウントとセッションを停止し、アプリ内権限を回収するとともに、オフライン閲覧用に端末へ取得したPDF等をアプリ側で削除する。未送信の編集データをサーバーへ反映する工程はない。削除の実施方法と確認方法は設計時に決める。IT担当者が退職する場合には、サービス管理者ロールを持つ職員がアプリ内の引き継ぎボタンから後任のIT担当者を指定する。利用者の元データを退職に伴って削除する意味ではない。
- 個人情報の保存：利用者ごとのPDF・評価・ニーズは事業所の正式な支援記録として扱う。アプリ側の現行版・履歴は利用終了後も最終サービス提供日から最低5年保持し、必要な延長事由を確認したうえで削除する。利用終了日と最終サービス提供日はサービス管理者またはIT担当者が登録・訂正する。論理削除・物理削除・バックアップ消去は第6.3節に従う。Drive上の移行元資料の破棄は本アプリの範囲外とし、端末の一時保存データはオンラインで削除指示を検知した時点で自動削除する。利用開始日から一律5年で削除する案は採用しない。
