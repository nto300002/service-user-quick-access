## 3. 論理データ定義

### 3.1 保存区分

| 区分 | 内容 | 原則 |
| --- | --- | --- |
| 正式記録 | 利用者別の公開済みPDF・評価・ニーズと過去版、公開に至る変更履歴 | 利用中は保持。利用終了後は6.3章の保存・削除規則に従う |
| 組織共通資料 | MVVと六つのニーズの参考PDFおよび版 | 利用者別の保存期限とは分ける。版の期間は要ヒアリング |
| 承認待ち資料 | 公開前の評価・ニーズ・PDF候補 | 閲覧画面には出さない。差し戻し後の保持期間は要ヒアリング |
| 端末保存版 | オフライン閲覧用の公開済み資料、同期状態、未送信の閲覧履歴 | 正式記録と別物。取得・削除・暗号化の方法は要技術検証 |
| 操作履歴 | 更新、公開、権限、引き継ぎ、削除、閲覧 | 個人情報を必要最小限とし、保存期間・閲覧権限は要ヒアリング |

### 3.2 エンティティ案

**ID、状態、更新日時は論理項目**であり、DBの型やテーブル分割は方式選定後に決める。利用者IDは内部識別子とし、氏名を主キーにしない。

| エンティティ | 主な項目 | 制約・関係 | 状態 |
| --- | --- | --- | --- |
| 職員 | 職員ID、表示名、認証主体ID、在籍状態、作成・停止日時 | 認証主体IDと職員IDを対応付ける。退職者は新規閲覧不可 | 設計案 |
| 権限割当 | 職員ID、ロールまたは個別権限、付与者、開始・終了日時 | 在籍職員だけ有効。IT担当者・サービス管理者は各1名を想定 | 前半は設計案、人数は仮決め |
| 登録端末 | 端末ID、職員ID、登録・停止日時、最終接続日時 | 停止端末のオンライン要求は拒否。オフライン削除の即時保証はしない | 仮決め／要技術検証 |
| 利用者 | 利用者ID、表示名、利用状態、利用終了日、最終サービス提供日 | アーカイブ後は通常一覧と同期対象から除外。日付訂正履歴を残す | 確定に基づく設計案 |
| 作業名 | 作業ID、名称、有効／削除状態、作成者、更新者、日時 | 削除後もIDと過去評価を保持。名称変更時の履歴表示はH-08 | 確定に基づく設計案 |
| 作業評価版 | 版ID、利用者ID、作業ID、評価値、申請者、申請・公開日時、公開版ID、注意表示 | 評価値は5記号または未入力。未入力と⬜︎は別。公開版は上書き消去しない | 確定に基づく設計案 |
| ニーズ版 | 版ID、利用者ID、メイン・サブの項目コード、アプローチポイント、申請者、公開日時 | 6項目の同一選択可。自由記述長の上限はH-04 | 確定に基づく設計案 |
| PDF版 | 版ID、対象ID、種類、ファイル参照、サイズ、検証値、申請者、公開日時 | 対象は利用者または組織共通。公開済み旧版を保持。原本の上書きは禁止 | 確定に基づく設計案 |
| 公開申請 | 申請ID、対象種別・ID、候補版ID、状態、申請者、確認者、理由、日時 | 候補版と現在の公開版を分離する。状態遷移は3.3節 | 設計案 |
| 参加予定 | 作業ID、利用者ID、対象日または現場ID、登録者 | 出発前判定に必要な場合のみ。登録方式はH-06 | 保留 |
| 端末同期状態 | 端末ID、資料ID、保存版ID、取得・検証日時、結果 | 未取得・成功・更新失敗・削除待ちを分ける | 設計案／要技術検証 |
| 閲覧履歴 | イベントID、職員ID、端末ID、利用者ID、資料種類・版ID、閲覧日時、送信日時 | オフライン再送で重複しない識別子を持つ | 記録要件は確定、識別子は設計案 |
| 操作履歴 | イベントID、実行者、操作、対象、前後の識別子、日時、結果、理由 | 引き継ぎ・削除・日付訂正などを記録。詳細本文の重複保存を抑える | 確定に基づく設計案 |
| 保全・削除案件 | 利用者ID、保存期限、延長理由、次回確認日、申請者、承認者、実行日時 | 最終サービス提供日未登録では申請不可。申請者と承認者は別人 | 確定に基づく設計案 |

### 3.3 公開申請の状態と整合性

| 遷移 | 実行者 | 表示・データ上の結果 |
| --- | --- | --- |
| 新規入力 → 確認待ち | 作業評価の担当職員、ニーズ編集権限者、PDF更新権限者 | 候補版を保存。公開版は変えない |
| 確認待ち → 公開済み | IT担当者 | 確認者・日時を記録し、対象の公開版参照を一括変更する |
| 確認待ち → 差し戻し | IT担当者 | 理由を記録。公開版は変えない。再提出方法はH-09 |
| IT担当者自身の申請 → 公開済み | 同じIT担当者が明示的に確認 | 申請と公開を別操作として記録する |
| 公開処理失敗 | システム | 旧公開版のまま、失敗を表示し、再操作可能にする |

**設計案：** 同一対象に複数の確認待ち候補があるときは、古い版を誤って公開しないよう、承認時に現在公開版の版IDを照合する。候補同士の優先順位と並行申請の扱いはH-09で確定する。PDFとの食い違いは自動判定が未確定のため、承認画面で職員が照合結果を明示する案とする。

### 3.4 アーカイブと削除

1. 利用終了日が登録されたらアーカイブし、通常一覧・新しい端末同期対象から外す。端末は次回オンライン接続時に対象の保存版を削除する。
2. 最終サービス提供日から5年を経過しても、同日が未登録、保全延長、調査・紛争対応がある場合は削除候補にしない。
3. IT担当者が削除を申請し、別職員のサービス管理者が承認する。同じ職員による申請・承認を拒否する。
4. 論理削除後30日以内の通常領域からの物理削除、さらに30日以内のバックアップからの消去と、復旧時の再公開防止を要件とする。具体的な実装・確認方法はT-08で検証する。

## 4. 権限詳細

### 4.1 ロールの意味

| ロール・権限 | 意味 |
| --- | --- |
| 職員 | 在籍し、アプリの利用権限を持つ人。全利用者の公開済み情報を閲覧できる |
| IT担当者 | 1名を想定。通常の権限付与、作業名削除、変更公開、端末停止、削除申請を担う |
| サービス責任者 | 利用者別・MVV・共通参考PDFの差し替えを行える。サービス管理者とは別の権限 |
| サービス管理者 | 1名を想定。IT担当者の引き継ぎ、正式記録の削除承認、利用終了日等の登録を行う |
| ニーズ編集権限 | IT担当者が職員に個別付与する編集権限 |
| 引き継ぎ代理 | サービス管理者が事前指定する。両者不在時のIT引き継ぎだけ実行できる |

### 4.2 操作別の権限表

表の「担当職員」は役職ではなく、該当する利用者の評価を入力する職員を指す。担当の判定方法はH-03で決める。複数のロールを持つ場合も、操作ごとの条件を満たす必要がある。

| 操作 | 許可する主体 | 追加条件・根拠 |
| --- | --- | --- |
| 公開済みの利用者情報・PDF・MVVを閲覧 | 在籍・利用許可済みの全職員 | 要件定義4章。閲覧履歴を残す |
| 作業名を追加・編集 | 全職員 | 要件定義10章。オンラインのみ |
| 作業名を削除 | IT担当者 | 過去評価を削除しない |
| 作業評価を入力・変更申請 | 担当職員 | 担当判定はH-03。公開はIT確認後 |
| ニーズ・アプローチポイントを変更申請 | IT担当者、ニーズ編集権限者 | 6項目の選択規則を適用 |
| 利用者別・MVV・共通参考PDFを差し替え申請 | IT担当者、サービス責任者 | オンラインのみ。初期移行はIT担当者 |
| 申請を公開・差し戻し | IT担当者 | 自身の変更も明示的な本人確認を要する |
| 通常の職員権限を付与・変更・停止 | IT担当者 | IT担当者自身の交代は別フロー |
| 端末を停止 | IT担当者、サービス管理者 | 紛失時を想定。オンライン停止と再接続時削除 |
| 利用終了日・最終サービス提供日を登録・訂正 | IT担当者、サービス管理者 | 変更前後・日時・実行者を残す |
| 保存期間終了後の削除を申請 | IT担当者 | 保全条件を確認する |
| 同申請を承認 | サービス管理者 | 申請者とは別の職員であること |
| IT担当者の後任を指定 | サービス管理者 | 通常経路。オンラインで5分以内に再認証 |
| IT担当者自身の後任を指定 | 現IT担当者 | サービス管理者が業務に就けない場合のみ。理由を記録 |
| 代理として後任を指定 | 事前指定の引き継ぎ代理 | 両者不在時のみ。理由を必須とし、通常の権限付与・削除承認は不可 |
| 閲覧履歴・操作履歴を検索・出力 | 未定 | H-10で閲覧者と保存期間を決める |

### 4.3 権限変更時の不変条件

- 初期IT権限は事前に決めた職員アカウントにだけ付ける。自主登録した別アカウントには付けない。本人と事前アカウントの紐付け方式はT-06。
- IT引き継ぎでは旧IT権限の回収と新IT権限の付与を一つの処理として行い、中間のIT担当者不在状態を作らない。旧担当者のオンラインセッションを失効させる。
- 引き継ぎ前5分以内のオンライン再認証、旧・新担当者の確認、代理理由、成功・失敗の履歴を要件とする。端末内の閲覧用再認証だけでは代用しない。
- 退職した職員のオンライン利用を止め、次回オンライン時に端末の保存版を削除する。通信できない端末への即時反映は保証しない。
- サービス管理者とサービス責任者を別の権限として扱う。同じ職員が兼ねても、削除申請と承認を同一人物に許さない。
